- Material-only estimates: math lives in pure `src/lib/material-estimate.ts` (unit-tested); AI only interprets geometry/material and its prices are ignored. Why: deterministic, auditable prices.
- Submission uploads use a shared helper and server-issued signed creation capabilities for random paths, with no direct client INSERT policy. Why: preserve guest forms without allowing arbitrary bucket writes.
- MCP tools require delegated OAuth with a client claim and forward the verified caller token through the shared client, never admin access. Why: external access must preserve user identity and existing RLS.
- `material_estimates` is service-role only (no anon/authenticated policies); customers receive only the DTO from `toCustomerDTO`. Why: never leak purchase cost or markup.
- Portfolio 3D: one persistent WebGL canvas per view (swap the model, never mount two scenes); quality tier, DPR caps and off-screen pausing live in src/components/portfolio/perf.ts. Why: avoid GPU stalls during transitions and on weak devices.
- Public service carousel cards use router links with real hrefs; hero media has a poster and pauses off-screen/hidden. Why: preserve keyboard/crawler navigation and avoid unnecessary video decoding.
- Admin Offer/Order Form PDFs: original templates (src/assets/templates/*.pdf.asset.json) are only filled, never redrawn; `admin_documents` is service-role only and sending requires an approved status plus a matching PDF SHA-256, claimed atomically. Why: exact templates, no unapproved or duplicate sends.
- Partner strip (src/components/xtz/PartnerMarquee.tsx) animates via one requestAnimationFrame loop writing transforms directly, pausing on hover/focus/drag/off-screen/hidden and for reduced motion; the first click/tap stops it and the next click on a logo opens that partner; partner projects live in `clients.ts` `projects`. Why: smooth infinite motion without per-frame React renders, and projects stay data-driven.
- Email → Notion sync lives in `src/lib/mail-sync/`: the mailbox is opened read-only (EXAMINE + BODY.PEEK, never STORE/MOVE/EXPUNGE/send), decision rules stay pure and unit-tested (`plan.ts`, `mime.ts`, `notion-map.ts`), live Notion writes and the website-form hook are gated by `mail_sync_settings` flags (default off), checkpoints never pass a failed message, and `mail_sync_*` tables are service-role only. Why: customer mail is never altered and nothing reaches Notion without explicit admin approval.
- Email/Website → Notion matching is one engine: pure `src/lib/mail-sync/canonical.ts` + `classify.ts` (tested) and `canonical.server.ts` (preview read-only; apply needs live_writes). One canonical request per real purchase, matched by submission ID → Order ID → email thread → same customer+subject window, else manual review (never merge by person alone); permanent TR-YYYY-NNNN Order IDs come from the shared atomic `allocate_order_code()` and are claimed via `mail_sync_claim_request`; reply state is recomputed from INBOX+Sent timestamps (only sends to the customer count), terminal/progressed statuses are preserved, owner-deleted records are never recreated, and automatic labels (Order Check, Classification) never overwrite a human change (`mail_sync_auto_labels`). Why: no duplicate orders, no false "replied", no silent identity changes.
- Notion Business OS views/page are configured through the Notion views API against the existing five databases only; scripts must update views by id and never create duplicate databases. Why: the owner's workspace is the single source of truth.
- Always-on Email → Notion: one pg_cron job (`toreo-mail-sync-*`) POSTs `{"mode":"live"}` to the final URL `https://www.toreo.gr/api/public/mail-sync` (redirecting hosts strip auth); the route accepts `MAIL_SYNC_TOKEN` or the scheduler token whose SHA-256 sits service-role-only in `mail_sync_cron_auth`, runs are locked/min-interval-limited and every run is recorded in `mail_sync_runs`; status for admin comes from `mail_sync_scheduler_status()`. Why: recurring sync without exposing credentials, overlapping runs or silent failures.
